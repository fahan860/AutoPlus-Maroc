1 Modèle de développement retenu
Comparatif des 5 modèles vus en cours (Génie Logiciel, Pr. Jebari Hakim) et choix justifié pour AUTO+
ModèlePrincipeAdapté à AUTO+ ?
CascadeÉtapes strictement séquentielles, on ne revient pas en arrière❌ Trop rigide — les besoins évoluent chaque semaine de stage
Modèle en VCascade + test associé à chaque étape de conception⚠️ Utile pour les modules critiques (paiement, auth) mais trop lourd pour tout le projet
SpiraleBoucles successives, chaque tour = analyse de risques + prototypage + mini-cascade✅ Adapté aux modules à risque technique élevé : agent IA darija/français, RAG, modèles ML (Semaine 4+)
Incrémental (Agile)Livraison par incréments utilisables, feedback rapide✅✅ Retenu comme modèle principal — correspond exactement au découpage réel du stage en semaines (Semaine 1 = setup, Semaine 2 = data garages, Semaine 3 = auth+RDV, ...)
Orienté réutilisationComposants/APIs existants (COTS)✅ Complémentaire — utilisé de fait (Express, pg, Zod, jsonwebtoken, Expo, GPT-4o/Mistral en API)
Modèle retenu : Incrémental (agile) comme cadre principal, avec une composante Spirale pour les modules à risque (IA/ML). Chaque semaine de stage = un incrément complet qui suit le mini-cycle en cascade (spécification → conception → codage → tests → livraison), exactement comme observé dans le code : Semaine 2 a livré le pipeline garages de bout en bout, Semaine 3 a livré auth+vehicles+interventions de bout en bout.

Détail des phases du modèle incrémental appliqué à chaque semaine (incrément) :

flowchart LR
    subgraph I1["Incrément Semaine N"]
        direction TB
        A1["1. Spécification
(besoins de la semaine)"] --> A2["2. Conception
(architecture + détaillée)"]
        A2 --> A3["3. Codage"]
        A3 --> A4["4. Tests
(unitaires + intégration)"]
        A4 --> A5["5. Livraison
(commit + démo)"]
    end
    A5 -.->|"feedback / ajustement"| B1
    subgraph I2["Incrément Semaine N+1"]

Pourquoi la spirale en complément : le cours insiste sur le fait que la spirale est adaptée quand "les exigences sont démesurées par rapport à la technologie maîtrisée". C'est exactement le cas de l'agent IA darija/français et du RAG pgvector prévus Semaine 4 — l'équipe ne maîtrise pas encore ces briques, donc chaque itération sur l'IA doit commencer par une analyse de risque + un prototype jetable avant tout codage définitif.

1 Analyse des besoins et faisabilité
Expression, recueil et formalisation des besoins du demandeur, estimation de la faisabilité technique et financière.
Appliqué à AUTO+ :
  • Besoin identifié : 18 000 besoins/jour en atelier au Maroc, 95% non digitalisés
  • Faisabilité technique validée dès Semaine 1 (Docker + PostgreSQL/PostGIS + API opérationnels, test /health réussi)
  • Faisabilité financière : stack open-source (Node.js, PostgreSQL, Redis) + coûts variables API (Google Maps, GPT-4o) reportés à la Phase Beta
2 Spécifications ou conception générale
Élaboration des spécifications de l'architecture générale du logiciel — définir CE que le logiciel doit faire (le "quoi").
Appliqué à AUTO+ :
  • Cas d'utilisation définis (Espace Client, Espace Mécanicien, Espace Admin, Espace Worker futur) — cf. AutoPlus_Diagrammes_Architecture.pdf et section 3 ci-dessous
  • Périmètre MVP explicitement séparé du périmètre futur (Phase 2/3 : IA, logistique)
3 Conception architecturale
Description de l'architecture du logiciel : identification de la structure globale, des composants principaux et de leurs relations.
Appliqué à AUTO+ :
  • Architecture 8 couches définie (Users → Entry Points → MVP Core → Platform Engine → Data Storage → AI Module → Logistics → Integrations)
  • Diagramme de déploiement réel (section 8) : conteneurs Docker (API / PostgreSQL+PostGIS / Redis)
4 Conception détaillée
Définition précise de chaque sous-ensemble du logiciel (structures de données, algorithmes), jusqu'à une forme permettant d'écrire directement les programmes.
Appliqué à AUTO+ :
  • Diagramme de classes/MCD (section 4) : structure précise des 6 tables et de leurs relations
  • Diagrammes de séquence (sections 5-6) : algorithme détaillé de chaque endpoint (validations, ordre des requêtes SQL, codes d'erreur)
  • Dictionnaire de données (section 9) : chaque colonne, type et contrainte
5 Programmation (le codage)
Traduction dans un langage de programmation des fonctionnalités définies lors des phases de conception.
Appliqué à AUTO+ :
  • Migrations SQL : api/migrations/001_create_garages.sql, 002_create_core_tables.sql
  • Routes Express : api/src/routes/garages.js, vehicles.js, interventions.js, middleware auth.js
  • Scripts de scraping/import : data/scrape_garages_osm.py, api/scripts/import_garages_csv.js
6 Tests unitaires / Tests d'intégration
Tests unitaires : vérifient individuellement que chaque sous-ensemble est implémenté conformément aux spécifications. Tests d'intégration : assemblent les parties pour obtenir un système exécutable et vérifient les interactions entre composants.
Appliqué à AUTO+ :
  • Test unitaire réalisé : curl http://localhost:3000/health → connexion DB confirmée (Semaine 1)
  • Test d'intégration réalisé : import CSV → UPSERT idempotent → 123 garages en base, relancé sans duplication
  • Manquant : suite de tests automatisés (Jest/Supertest) pour les routes vehicles/interventions — à ajouter au plan de tests
7 Vérification
Vérifier la conformité du logiciel aux spécifications globales (le système fait-il ce qui était prévu ?).
Appliqué à AUTO+ :
  • Prototype cliquable (docs/prototype_mobile_app.html) utilisé pour vérifier visuellement que le cycle de vie du RDV correspond bien au diagramme d'état-transition (section 7) avant tout développement mobile réel
  • Rapport d'avancement (RAPPORT_AVANCEMENT.md) : tableau des écarts entre prévu et réalisé, mis à jour chaque semaine
8 Maintenance
Actions correctives (maintenance corrective) et évolutives (maintenance évolutive/perfective) sur le logiciel après mise en service.
Appliqué à AUTO+ :
  • Maintenance corrective déjà vécue : restauration de merge_and_clean_garages.py et import_garages_csv.js après une corruption d'écriture (commit 8ea0a90)
  • Maintenance évolutive prévue : enrichissement des 42 garages sans téléphone, ajout de l'historique véhicule par plaque (Semaine 4)

4 Scénarios d'utilisation détaillés
Fiches de cas d'utilisation (acteur, préconditions, scénario nominal, scénarios alternatifs, postconditions) — pour les cas déjà couverts par le code de la Semaine 3
RubriqueDétail
NomPrendre rendez-vous (RDV)
Acteur principalClient (automobiliste)
Acteurs secondairesUser (mécanicien du garage visé)
PréconditionsLe client est authentifié (JWT valide, rôle = automobiliste) ; le client possède au moins un véhicule enregistré ; le garage visé existe
Scénario nominal 1. Le client recherche un garage depuis l'écran d'accueil
2. Il consulte le profil du garage (note, avis, coordonnées)
3. Il sélectionne "Prendre rendez-vous"
4. Il choisit son véhicule, le type de panne, décrit le problème, choisit une date/heure
5. Le système vérifie que le véhicule appartient bien au client et que le garage existe
6. Le système crée l'intervention avec le statut demande
7. Le système journalise l'événement rdv_demande
8. Le client reçoit la confirmation d'envoi de sa demande
Scénarios alternatifs / exceptions A1. Token absent/invalide → 401 Token manquant/invalide
A2. Champs du formulaire invalides (schéma Zod) → 400 Bad Request
A3. Véhicule inexistant ou n'appartenant pas au client → 404 Véhicule introuvable
A4. Garage inexistant → 404 Garage introuvable
PostconditionUne nouvelle ligne interventions existe avec statut demande ; elle apparaît dans le dashboard du mécanicien du garage concerné
RubriqueDétail
NomTraiter une demande de RDV
Acteur principalUser (mécanicien)
PréconditionsLe mécanicien est authentifié (rôle = mecanicien) et rattaché à un garage (garage_id) ; une intervention existe pour ce garage
Scénario nominal 1. Le mécanicien consulte la liste des demandes reçues pour son garage
2. Il sélectionne une demande au statut demande
3. Il choisit "Confirmer" (ou "Refuser")
4. Le système vérifie que l'intervention appartient bien à son garage
5. Le système met à jour le statut (confirme ou annule) et journalise rdv_statut_change
6. Le mécanicien répète l'opération pour faire avancer le statut jusqu'à en_cours puis termine
Scénarios alternatifs / exceptions A1. Rôle incorrect (client essaie d'appeler la route) → 403 Accès refusé
A2. Statut demandé hors de l'énumération autorisée → 400 Bad Request
A3. Intervention inexistante pour ce garage → 404 Intervention introuvable pour ce garage
PostconditionLe statut de l'intervention est mis à jour ; le client peut le consulter dans "Mes RDV"
RubriqueDétail
NomRechercher un mécanicien / garage
Acteur principalClient (automobiliste, authentifié ou non)
PréconditionsAucune (consultation publique du répertoire de garages)
Scénario nominal 1. Le client ouvre l'écran d'accueil
2. Le système affiche la liste des garages (nom, catégorie, note, avis)
3. Le client consulte le profil détaillé d'un garage (adresse, téléphone)
Scénarios alternatifs / exceptionsAucun garage à proximité → liste vide affichée avec message dédié (à implémenter)
PostconditionAucune (lecture seule) ; événement recherche_garage journalisé pour le futur modèle de recommandation

8 Diagramme de séquence — Prise de RDV
Correspond au cas d'usage détaillé p.4 de AutoPlus_Diagrammes_Architecture.pdf, ici au niveau technique (route réellement codée : POST /interventions)
sequenceDiagram
    actor C as Client (App mobile)
    participant A as API Express /interventions
    participant M as Middleware Auth (JWT)
    participant DB as PostgreSQL
    participant EV as Events (Redis)

    C->>A: POST /interventions {vehicle_id, garage_id, type_panne, ...} + Bearer token
    A->>M: requireAuth + requireRole('automobiliste')
    M->>M: jwt.verify(token)
    alt token invalide ou role incorrect
        M-->>C: 401 / 403
    else token valide
        M-->>A: req.user {id, role}
        A->>A: validation Zod du body
        alt body invalide
            A-->>C: 400 Bad Request
        else body valide
            A->>DB: SELECT vehicle WHERE id AND user_id
            DB-->>A: vehicule (ou vide)
            alt vehicule introuvable
                A-->>C: 404 Vehicule introuvable
            else vehicule trouve
                A->>DB: SELECT garage WHERE id
                DB-->>A: garage (ou vide)
                alt garage introuvable
                    A-->>C: 404 Garage introuvable
                else garage trouve
                    A->>DB: INSERT INTO interventions RETURNING *
                    DB-->>A: nouvelle intervention (statut=demande)
                    A->>EV: logEvent('rdv_demande', ...)
                    A-->>C: 201 Created (intervention)
                end
            end
        end
    end
9 Diagramme de séquence — Traitement du RDV par le mécanicien
Route PATCH /interventions/:id/statut — suite logique du cas 2, cycle de vie complet de la demande
sequenceDiagram
    actor Me as Mecanicien (Dashboard)
    participant A as API Express /interventions/:id/statut
    participant M as Middleware Auth (JWT)
    participant DB as PostgreSQL
    participant EV as Events (Redis)

    Me->>A: PATCH /interventions/42/statut {statut: "confirme"} + Bearer token
    A->>M: requireAuth + requireRole('mecanicien')
    M-->>A: req.user {id, role: mecanicien}
    A->>A: validation Zod (statut in enum autorise)
    A->>DB: SELECT garage_id FROM users WHERE id = user.id
    DB-->>A: garage_id du mecanicien
    A->>DB: UPDATE interventions SET statut WHERE id AND garage_id
    alt intervention introuvable pour ce garage
        DB-->>A: 0 ligne
        A-->>Me: 404 Intervention introuvable pour ce garage
    else mise a jour reussie
        DB-->>A: intervention mise a jour
        A->>EV: logEvent('rdv_statut_change', ...)
        A-->>Me: 200 OK (intervention)
    end
